## Findings

**What:** SWE-bench Verified has saturated — top models reach ~75% (e.g. GPT-5.2) while the full/harder leaderboard sits near 40%; OpenAI stopped evaluating on it in early 2026 because public task leakage into training data means gains reflect data exposure rather than capability gain.
**Why it matters:** Any benchmark number cited for a coding agent/model choice should be treated skeptically if it's SWE-bench-only and undated; the field's own leading labs no longer trust it as a sole signal.
**Confidence:** med (aggregated from KDnuggets/OpenHands blog summaries, not a primary lab statement)

**What:** New benchmarks explicitly target what SWE-bench misses: SWE-bench Pro (harder, multi-file, contamination-resistant), SWE-Compass (8 languages, multiple task types), Terminal-Bench/LongCLI-Bench (broader CLI interaction beyond patching), SetupBench (environment setup), SEC-bench (security workflows), SWE-EVO (long-horizon software evolution).
**Why it matters:** These map far more closely to what a PO+swarm workspace actually asks agents to do (multi-file changes, environment setup, long-horizon tasks across sessions) than the original single-PR-patch SWE-bench format.
**Confidence:** med (single aggregator source cross-referencing arXiv titles; individual benchmark claims not independently verified)

**What:** A 2026 study ("Rethinking the Value of Agent-Generated Tests") found GPT-5.2 resolves 71.8% of tasks while writing tests in only 0.6% of runs, vs. Claude Opus 4.5 at 74.4% success with 83% test-writing — a 2.6-point outcome gap despite radically different testing behavior, meaning test-writing is model-dependent "style," not causally linked to success.
**Why it matters:** Directly counters the intuitive assumption that "more agent-written tests = more reliable agent output" — the correlation is weak. Also: encouraging test-writing increased GPT-5.2 token usage 19.8% with no resolution-rate gain; discouraging it cut Kimi K2 Thinking input tokens 49% for only a 2.6% performance drop.
**Confidence:** med (single arXiv study, not yet independently replicated)

**What:** Agent-written tests are observational rather than verification-focused: 69-77% rely on print-statement-style value revelation rather than assertions; when assertions do appear, they favor exact-value/property checks over relational constraints.
**Why it matters:** A green test suite generated by an agent is a weaker correctness signal than a human-written one — QA gates that just check "tests pass" may be insufficient without also checking assertion density/quality for agent-authored tests.
**Confidence:** med (same single study as above)

**What:** A separate 2026 empirical study on over-mocking found coding agents add mocks in 36% of test commits vs. 26% for human developers (36% vs 28% in high-agent-activity repos specifically), and 68% of repos with agent test activity also show agent mock activity. Agents use almost exclusively the "mock" type (95%) vs. humans' varied mix of mock/fake/spy (91%/57%/51%).
**Why it matters:** Concrete, measurable test-quality regression pattern specific to agentic code: heavier, less-varied mocking produces tests that validate less real interaction and drift from implementation over time — a maintenance-burden risk that compounds across a large agent-generated codebase.
**Confidence:** med (single arXiv empirical study)

**What:** The same over-mocking study's concrete recommendation: put explicit mocking guidance into agent configuration files (they name `CLAUDE.md` specifically) — e.g. when to use fakes/spies vs. mocks, and require human review of agent-generated test mocking choices.
**Why it matters:** This is a directly actionable, low-cost mitigation — a policy line in a project's `CLAUDE.md`/testing rules — rather than a tooling change.
**Confidence:** med

**What:** The "Agentic SDLC" framing (TestQuality, 2026) describes LLM-generated code as prone to a "silent gray error" pattern: code passes compilation and unit tests while implementing incorrect business logic, which traditional QA pipelines don't catch. Mitigation trend: feed agents structured context (AST parses, dependency graphs, architectural constraints) so generated code reflects real system semantics, not just locally-plausible syntax.
**Why it matters:** Reinforces (from the testing angle specifically) the already-logged finding that context-breadth, not model choice, is the biggest lever for agent code quality — here applied to test/verification correctness rather than review.
**Confidence:** low-med (vendor blog framing, not a controlled study)

**What:** Multi-agent test-generation research (e.g. TestAgent-style designs) proposes splitting test generation into specialized roles — a requirement planner, a test generator, and a test reviewer — backed by a test-specialized knowledge graph built from static analysis of code entities and dependencies, rather than one agent doing planning+writing+reviewing in one pass.
**Why it matters:** Directly parallel to this workspace's PO+swarm model applied one level down (inside a single coding task): role-separation for test generation could reduce the "process style, not outcome" problem noted above by giving a dedicated reviewer role veto power over low-quality/over-mocked tests before they land.
**Confidence:** low (research-stage proposal, not yet a widely adopted practice)

## For This Workspace
- Add an explicit mocking-guidance line to this repo's `CLAUDE.md`/testing conventions (mirroring the study's own recommendation) before any future swarm task involves generating tests for `.agent-harness/tools/` scripts or dashboard code — specify when mocks vs. fakes vs. real fixtures are expected.
- When a build/QA-swarm subagent reports "tests pass" as its verification, treat that as necessary but not sufficient for agent-generated test suites specifically — spot-check assertion density (are these real assertions or print/observation statements?) as part of the PO QA gate, not just exit-code 0.
- If this workspace ever benchmarks or compares coding-agent/model choices for swarm work, cite at least two benchmarks (not SWE-bench alone) and prefer ones matching the actual task shape (Terminal-Bench for CLI/tool-heavy tasks, SetupBench for environment/deploy tasks) over generic leaderboard scores.
- Consider the TestAgent-style role split (planner/generator/reviewer) as a template for a future "test-generation swarm" delegation contract, with the reviewer role specifically empowered to reject over-mocked or assertion-free tests before they're merged.
